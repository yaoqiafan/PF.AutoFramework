# SecsGem 服务独立与托盘程序设计稿

- **状态**：草案，待讨论（管理界面内容另行讨论）
- **日期**：2026-11-19
- **排期**：`audit/framework-review-2026-11` 合并 main 之后开工

---

## 1. 背景：现在的问题

### 1.1 每个项目各拷一份服务源码，版本已经分叉

2026-11-19 比对 `PF.SecsGem.Service/Worker.cs`：

| 位置 | 行数 |
|---|---|
| 框架 `Standard Library\PF.AutoFramework` | 789 |
| `AutoOCR\KLT_DualWorkstation` | 703 |
| `AutoOCR\KLT_SingalWorkstation` | 740 |
| `MappingShift\MotionControl` | 746 |

4 份内容各不相同。各项目安装包通过 `installer.conf` 的 `SERVICE1_CSPROJ=..\PF.SecsGem.Service\...` 编译**自己那份副本**，后果是：

- 框架里的服务端修复（S9F1 字节序、Deselect/Separate、主程序断开时复位 Host 状态、HSMS 长度头校验等）到不了现场。MappingShift 的副本曾长期停在 7 月版。
- 服务全机唯一（服务名固定 `SecsGemService`），一机多项目时**最后安装的项目说了算**，现场实际运行的服务版本不可控。
- 服务各副本里没有任何项目定制，项目差异只有 `appsettings.json` 的 `ProjectName`（由安装脚本注入）。各留一份没有必要。

### 1.2 服务状态对现场不可见

服务没有界面。现场想确认"服务在不在、主程序接没接入、Host 连没连上"，只能翻日志或打开服务管理器，排查成本高（参考 2026-11-19 现场反馈的"Host 发 S1F1 不回复"问题）。

---

## 2. 目标与非目标

**目标**
1. SecsGem 独立成一个项目，**单一源码、单独版本、单独安装包**。
2. 增加托盘程序：不弹主窗口，只在系统托盘显示图标，右键菜单提供基础操作和管理界面入口。
3. 管理界面和敏感操作需要超级用户校验，**不查数据库**，规则与框架一致。
4. 各项目的主程序安装包不再携带服务。

**非目标（本期不做）**
- 不改变服务"开机自启、与是否登录无关"的运行方式。
- 不改 HSMS / SECS 报文处理逻辑。
- 管理界面的具体内容（见第 8 节，另行讨论）。

---

## 3. 总体结构

```
PF.SecsGem（独立项目，单独解决方案与安装包）
├─ PF.SecsGem.Service      Windows 服务：开机自启、无界面，职责与现在相同
├─ PF.SecsGem.Tray         托盘程序：用户登录后自启，运行在用户桌面会话
│      ↕ 管理通道（命名管道，与 6800 本机通道分开）
└─ PF.SecsGem.Contracts    两端共用的协议定义（发 NuGet 包，主程序也引用）
         · 本机通道：端口 6800、帧命令字节（0x00 报文 / 0x02 状态 / ...）、协议版本号
         · 管理通道：管道名、命令与应答结构
```

依赖方向：`PF.SecsGem.*` 通过 NuGet 引用框架的 `PF.Core`、`PF.Infrastructure`、`PF.SecsGem.DataBase`、`PF.Services`。这些包已在私服发布，没有障碍。

### 3.1 为什么必须是两个进程

从 Windows Vista 起，服务运行在 **Session 0**，与用户桌面隔离。服务进程创建的窗口和托盘图标，用户都看不到。所以托盘只能是单独的用户态程序。

也不考虑"取消服务、只保留托盘程序"：那样必须有人登录才会运行，有人退出托盘 SECS 就跟着断，而开机自启、与登录无关正是当初用服务的原因。

## 4. 通道设计

### 4.1 本机通道（6800，主程序 ↔ 服务）

保持现状，增加**协议版本握手**：

- 主程序接入后，服务先推送一帧协议版本号（新增命令字节），再推状态帧。
- 主程序（`InternalClient`）比对 `Contracts` 里的版本号，不兼容时报警。报警文案要写明双方版本，以及应该升级哪一边。
- 旧服务不发版本帧：主程序在超时（如 2s）内没收到，按"旧版本服务"告警，但不阻断。

**为什么现在必须做**：服务独立后，它和主程序分属两个发布节奏。新旧混搭在现场是必然会出现的，没有握手时表现为"Host 连上了但不回报文"这类难查的问题。

### 4.2 管理通道（命名管道，托盘 ↔ 服务）

- **托盘绝不能连 6800**：服务把 6800 上新接入的连接一律当作主程序（`Worker.LocationServer_ClientConnected` 直接覆盖 `LocationClientId`），托盘连上会抢走主程序的通道。
- 采用命名管道，例如 `\\.\pipe\PF.SecsGem.Manage`。管道 ACL 只允许本机交互用户和 SYSTEM 访问，不对网络开放。
- 第一期只读：服务状态快照（HSMS 是否监听、监听地址端口、主程序是否接入、Host 是否连接与连接时长、收发计数、绑定的 ProjectName、服务版本与协议版本）。
- 写操作（如修改配置、断开 Host）放到第二期，与管理界面一起讨论。

## 5. 托盘程序

### 5.1 运行方式
- 由安装包写入 HKLM `Run` 项，对所有用户登录自启。每个登录会话只允许一个实例。
- 托盘图标按状态显示（颜色或角标示意）：
  - 服务未运行
  - 运行中但主程序未接入（HSMS 未监听）
  - 主程序已接入、等待 Host
  - Host 已连接
- 鼠标悬停提示：当前状态、绑定的 ProjectName、HSMS 地址端口。

### 5.2 右键菜单（第一期草案）

| 菜单项 | 是否需要超级用户 |
|---|---|
| 状态摘要（只读） | 否 |
| 打开服务日志目录 `D:\PF_Logs\SecsGem\Service\` | 否 |
| 打开协议日志目录 `...\Protocol\` | 否 |
| 启动 / 停止 / 重启服务 | **是** |
| 打开管理界面 | **是** |
| 关于（服务版本、协议版本、托盘版本） | 否 |
| 退出托盘（不影响服务） | 否 |

### 5.3 启停服务的权限
普通用户调用 SCM 启停服务会被系统拒绝。方案：**安装时用 `sc sdset` 给本机交互用户授予 `SecsGemService` 的启动、停止、查询权限**，托盘不必每次弹 UAC。安装包里要写明具体 SDDL 并经过验证。

备选方案：只在执行启停时以管理员身份重新启动一个小进程完成操作。

## 6. 超级用户校验

- **规则与框架一致**：用户名 `SuperUser`（不区分大小写），密码为本机当前时间 `yyyyMMddHH00`（见 `PF.Services/Identity/UserService.cs` 的 `LoginAsync`）。
- **不复制规则，抽成共用代码**：把规则提到 `PF.Core`，例如静态的 `SuperUserCredential.Verify(userName, password, now)`。`UserService` 和托盘程序都调用它，"规则一致"由代码保证，以后改规则只改一处。
- **不查数据库**：托盘不连 `SystemParamsCollection.db`，也就不依赖任何项目的配置目录。
- 管理界面登录后有会话超时（时长待定），超时后重新校验。
- 已知风险（与主程序相同，已记入审计遗留清单）：规则可以推算，强度有限。

## 7. 安装、升级与项目绑定

### 7.1 安装包
- 独立安装包同时包含服务和托盘程序，负责：
  - 注册服务
  - 设置 `sc sdset`
  - 写入 Run 项
  - 检查 .NET 8 运行时
- 服务注册沿用已验证的做法：`net stop` 同步等待 → `sc delete` → 重试 `sc create` 最多 15s，失败时弹框；卸载时只删除 ImagePath 指向本安装目录的服务。
- 2026-11-19 做过一个临时验证版（Inno Setup，单服务、`ProjectName` 写死），可作为起点。

### 7.2 ProjectName
- 服务仍从 `appsettings.json` 的 `ProjectName` 读取项目名，读不到时拒绝启动（现有逻辑）。
- 独立安装包在安装向导里**让人选择或填写 ProjectName**：枚举 `D:\PFConfig\PFAutoFrameWork\` 下含 `SecsGemConfig.db` 的子目录供选择，也允许手填。
- 主程序启动时的归属校验（`VerifySecsServiceProjectBinding`）比较的就是这个值，不比较安装路径，所以服务装在哪个目录都可以。

### 7.3 项目侧的迁移
1. 删除各项目里的 `PF.SecsGem.Service` 副本（目前 KLT_DualWorkstation、KLT_SingalWorkstation、MappingShift/MotionControl 三处）。
2. 各项目 `installer.conf` 设 `SERVICE_COUNT=0`，主程序安装包不再带服务。
3. 现场部署顺序改为"先装服务包，再装主程序包"，或者两者独立升级。
4. 框架仓库原 `PF.SecsGem.Service` 移入新项目，`AGENTS.md` 的架构图和相关说明同步更新。

## 8. 待讨论

1. **管理界面内容**：实时报文监视、连接状态、配置查看和修改、最近错误。
2. **配置修改权归谁**：`SecsGemConfig.db` 目前由主程序 SECS 调试页写入。托盘要不要也能改？两边同时修改时以谁为准？改完后谁通知服务生效？现在是主程序断开重连后重读配置。
3. **一机多项目**：托盘是否显示或切换服务当前绑定的项目，切换时如何处理正在运行的主程序。
4. **新仓库还是同仓库独立解决方案**：本稿按独立项目设计，协议靠 `Contracts` 包和版本握手保持一致。
5. **托盘 UI 技术**：WPF（复用 PF.UI.Resources 风格）还是 WinForms（`NotifyIcon` 原生、体积小）。
6. **会话超时时长**，以及托盘的操作要不要记操作日志。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 本机通道协议跨仓库演进，新旧混搭 | `Contracts` 包 + 协议版本握手（4.1） |
| `sc sdset` 写错导致服务无法管理 | 安装包固定 SDDL，上线前在干净机器上验证；卸载时恢复默认 |
| 托盘误连 6800 抢占主程序通道 | 管理走命名管道；可考虑服务侧校验 6800 首帧身份 |
| 迁移期间现场有的机器还是旧的捆绑安装 | 新服务安装包能接管旧注册（sc delete + create）；主程序归属校验照常提示 |
