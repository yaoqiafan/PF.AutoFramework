# 现场升级迁移说明 — 配置目录按项目隔离

> **适用范围**：从「无项目隔离」的旧版本（PF.Application.Base ≤ 1.0.4）升级到引入项目隔离的新版本。
> **必读**：这是**破坏性变更**。不执行迁移，升级后主程序会读不到任何已有配置（参数、硬件、通讯、配方、点表全部回到默认值），SecsGem 服务会拒绝启动。

---

## 1. 改了什么

配置路径从共享的一个目录，改为按项目名分子目录：

```
旧：D:\PFConfig\PFAutoFrameWork\SystemParamsCollection.db
新：D:\PFConfig\PFAutoFrameWork\{项目名}\SystemParamsCollection.db
```

`{项目名}` 默认等于主程序入口程序集名（如 `PF.Application.Shell`）。

### 为什么要改

`AppParamDbContext.EnsureDefaultParametersCreatedAsync` 在启动时会清理"不在本项目默认参数集里"的参数行——这是设计如此的废弃参数清理逻辑。但当同一台机器上换一个项目的程序运行时，A 项目的参数在 B 项目眼里全都是"废弃行"，于是被整批删除。参数、硬件配置、通讯配置四张表都会被清空。

除数据库外，`Recipe\`、`AxisPoints\`、`DataMemory\`、`user.config` 等也都存在同名互相覆盖的问题。

### 服务侧联动

`PF.SecsGem.Service` 是独立进程，开机自启（`start= auto`）时主程序可能还没运行过，运行期无法向任何人询问自己属于哪个项目。因此项目名在安装时由安装器写入服务目录的 `appsettings.json`：

```json
{ "ProjectName": "PF.Application.Shell", "Logging": { ... } }
```

服务读不到这个键时**拒绝启动**（而不是回退到旧路径）——各设备的 `SecsGemConfig.db` 内容不同，回退会让服务用一个空库去跟 Host 建链，外部看是"正常运行"，实际设备号、CEID/VID 全错。这种静默错误比服务起不来危险得多。

**服务名保持 `SecsGemService` 不变，不按项目区分**。原因：服务的本机通道端口 6800 在服务端（`Worker.LocationServer`）和主程序端（`InternalClient`）都是硬编码的，HSMS 被动端口也只有一个，一台机器上同时只可能有一个实例真正工作。若按项目注册多个 `start= auto` 的服务，开机时它们会争抢 6800，谁抢到不确定，反而让"当前生效的是哪个项目的配置"变得不可预测。

一机多项目时，后装的安装包会覆盖注册（`sc delete` + `sc create`），服务归属最后安装的项目。主程序启动时会解析 SCM 中**实际注册**的 `ImagePath`，读取该服务目录下的 `appsettings.json` 比对项目名——不一致就弹窗提示「当前注册的 SECS/GEM 服务属于项目 X」，处理方式是重新运行本项目的安装包接管服务。

## 2. 迁移步骤

### 2.1 停止所有相关进程

1. 退出主程序（正常退出，不要用任务管理器强杀——SQLite 需要 checkpoint）
2. 打开「服务」管理器，停止 `SecsGemService`

### 2.2 预演一次（不实际改动）

以**管理员身份**打开 PowerShell：

```powershell
cd <安装包所在目录>\Installer
.\Migrate-Config.ps1 -ProjectName PF.Application.Shell -WhatIf
```

`-ProjectName` 填该现场实际的项目名。核对打印出来的待迁移条目清单是否符合预期。

### 2.3 正式迁移

```powershell
.\Migrate-Config.ps1 -ProjectName PF.Application.Shell
```

脚本会：

1. 检查是否还有 `SecsGemService*` 在运行（有则中止；若确认该服务与本机台无关，可加 `-Force` 降级为告警）
2. 检查 `*.db-wal` 是否为 0 字节（非 0 会告警，提示可能有进程没退干净）
3. 把整个 `D:\PFConfig\PFAutoFrameWork` 打包备份到 `D:\PFConfig\PFAutoFrameWork_backup_{时间戳}.zip`
4. 把根目录下所有文件和目录**移动**到 `D:\PFConfig\PFAutoFrameWork\{项目名}\`
5. 在目标目录写一个 `.pf-project` 标记文件（后续迁移别的项目时据此跳过已迁移的目录）

> **为什么是整体搬而不是按白名单搬**：根目录下除框架自带的 4 个数据库和几个配置文件外，还混杂着各下游项目自己产生的文件（`Email.db`、`EnvHistory.db`、`Storage.db`、`StorageLog.db`、`WaferComparison.db`、`SiloTypes.json`、`EmailOptions.json`、`StorageOptions.json`、`Region\`、`AxisPoints\` 等）。白名单一定会漏，漏掉的在新布局下读不到，等同配置丢失。

> **为什么是移动而不是复制**：复制会在根目录留一份残留，下次再有别的项目升级时会被二次认领，反而制造混乱。备份 zip 已经承担了兜底职责。

### 2.4 安装新版本

运行新版安装包。它会：

- 把 `ProjectName` 写进服务的 `appsettings.json`
- 重新注册 `SecsGemService` 服务，binPath 指向本次安装目录
- 注册表键改写为 `HKLM\SOFTWARE\PowerFocus\PFAutoFramework\{项目名}`（旧版误用了带空格的 `PF AutoFramework` 作键名，与代码读取的键名对不上，导致 InstallPath 查找恒失败并静默回退到 Program Files）

### 2.5 验收

| # | 检查项 | 预期 |
|---|--------|------|
| 1 | 启动主程序，Splash 阶段 | 不弹出「配置校验」告警 |
| 2 | 参数页 / 硬件页 / 通讯页 | 数据与升级前一致 |
| 3 | 配方页 | 配方列表完整 |
| 4 | 调试页各机构点表 | 点位坐标与升级前一致 |
| 5 | 报警历史 / 生产记录 | 历史数据可查 |
| 6 | 服务管理器 | `SecsGemService` 存在且「正在运行」，其可执行文件路径指向本次安装目录 |
| 7 | SECS 面板 | 服务状态「运行中」，SECS 配置数据完整 |

---

## 3. 回滚

1. 停止主程序和 `SecsGemService` 服务
2. 卸载新版本
3. 删除 `D:\PFConfig\PFAutoFrameWork` 下的全部内容
4. 把备份 zip 解压回 `D:\PFConfig\PFAutoFrameWork`
5. 安装旧版本

## 4. 常见问题

**Q：主程序启动弹「配置校验」告警说服务属于另一个项目？**
A：一机多项目时，当前注册的服务是另一个项目的安装包装的——重新运行本项目安装包接管即可。

（项目在 `App.xaml.cs` 里重写 `ProjectName` 不会导致这个问题：安装器会直接从源码读取该字面量，`installer.conf` 的 `PROJECT_NAME` 保持留空即可。只有当 `PROJECT_NAME` 被填了且与源码不一致时，构建期就会失败，不会出包。）

**Q：服务起不来，事件查看器里有 FATAL 记录？**
A：看 `D:\PF_Logs\SecsGem\Service\startup-error.log`。多半是 `appsettings.json` 缺 `ProjectName` 键。可临时用命令行覆盖排查：`sc create ... binPath= "x.exe --ProjectName=Foo"`，或设服务级环境变量 `ProjectName`。

**Q：一台机器上要装两个项目？**
A：配置目录、注册表键都按项目名隔离，两个项目各自迁移一次即可（第二个项目迁移时根目录已经空了，直接建新目录）。但 **SECS/GEM 服务全机只有一个**，归属最后安装的那个项目——因为它的本机通道端口 6800 两端硬编码、HSMS 被动端口也唯一，本来就不可能同时跑两份。要切换到另一个项目做 SECS 联机时，重新运行那个项目的安装包接管服务即可；不联机的话可以忽略启动时的校验告警。

**Q：能不能不迁移，让程序自动搬？**
A：本版本刻意不做自动迁移。现场数量可控，自动迁移在"哪些文件属于哪个项目"这个判断上无法做到可靠，误搬的代价高于人工执行一次脚本。
